Claude Code Sub-Agents

These are autonomous AI agents that run as Claude Code subprocesses to power the recruiting pipeline CLI. Each agent reads a JSON artifact, performs its specialized task, and writes the next artifact in the chain — fully orchestrated with human-in-the-loop checkpoints.

JD Extraction
.claude/agents/jd-extraction.md
STAGE 1
Read Write

Reads the raw job description from 00_input.json, applies a 3-step extraction process, and produces a fully typed SearchSpec with skills, seniority, location, and quality scoring.

1. Clean → 2. Gap Fill → 3. Extract
  • Rates JD quality 0–10 based on clarity, structure, and completeness
  • Infers skills via role knowledge — e.g. "Python Engineer" adds Docker, Git, CI/CD
  • Flags unrealistic combinations and missing sections as gap_flags
  • Rewrites low-quality JDs into clean structured prose
  • Supports inline text or file path input (.txt, .md, .pdf, .json)
  • Outputs canonical role_title, seniority_level, must/nice/inferred skills
Reads
00_input.json — raw_jd, jd_file_path, weights, thresholds
Writes
01_search_spec.json — SearchSpec with must_have_skills, nice_to_have_skills, inferred_skills, quality score
Query Generation
.claude/agents/query-generation.md
STAGE 2
Read Write

Reads the search spec and generates Boolean search queries for 5 job boards via site: operators, LinkedIn profiles via Google CSE, Naukri keyword API, and PDL field-based queries.

  • 5 job boards: Naukri, Indeed, Shine, Foundit, TimesJobs — each with site: queries
  • LinkedIn: site:linkedin.com/in Boolean queries via Google CSE
  • Naukri API: keyword-style format with title + skills + location + experience range
  • PDL: structured field expressions for /person/search API
  • 3 primary + 2 fallback queries per source (25+ total queries)
  • mode=web skips API-only sources; mode=api generates all four sections
Reads
01_search_spec.json — role_title, skills, seniority, location
Writes
02_query_set.json — job_boards{naukri,indeed,shine,foundit,timesjobs}, google_cse, naukri, pdl
Profile Fetching — API
.claude/agents/profile-fetching-api.md
STAGE 3a
Read Write Bash

Calls live APIs via curl — Google Custom Search v1, People Data Labs v5 Person Search, and Naukri Resdex. Enforces strict evidence rules: every profile must originate from a real API response received in this session.

  • Google CSE v1: customsearch/v1 — extracts name, title, skills from title + snippet
  • PDL v5: /person/search — full profiles with experience, education, linkedin_url
  • Naukri Resdex: enterprise endpoint (requires contract credentials)
  • Zero invented data — must print raw API response before extracting any profile
  • URL validation via curl HEAD checks: 200/301/302 kept, 404 nulled
  • Data quality tagging: full_page (PDL), snippet_only (CSE), partial (Naukri)
Reads
02_query_set.json + .env (GOOGLE_CSE_KEY, PDL_KEY, NAUKRI_KEY)
Writes
03_raw_profiles.json — RawProfile[] with source_availability map
Profile Fetching — Web
.claude/agents/profile-fetching-web.md
STAGE 3b
Read Write WebSearch WebFetch

No API keys needed. Uses WebSearch to find candidates on job boards first (primary source), then LinkedIn. Fetches the top 10 URLs with WebFetch and classifies each page as live, login_wall, partial, or dead.

  • Job boards first: Naukri and Indeed as primary; Shine/Foundit/TimesJobs as bonus if pool < 6
  • LinkedIn second: fallbacks triggered if primaries return < 5 results
  • Fetches top 10 most promising URLs — job board URLs always prioritized
  • Classifies url_status: live (profile content visible), login_wall, partial, dead
  • Skips job listing URLs containing /job/, /vacancy/, /apply/
  • Merges same-person results across boards; stores secondary URLs as alt_urls
  • Auto-fallback: if primary[0] returns 0 results, tries fallback[0] immediately
Reads
02_query_set.json — job_boards.{naukri,indeed} + google_cse queries
Writes
03_raw_profiles.json — RawProfile[] with alt_urls, url_status, data_quality
Candidate Deduplication
.claude/agents/candidate-deduplication.md
STAGE 4
Read Write Bash

P1–P4 identity resolution across all sources. Writes Python scripts for deterministic matching, merges duplicates with source-priority field selection, and preserves alt_profiles for URL recovery downstream.

P1 Email → P2 Name+Company → P3 Name+Title+Loc → P4 Phone
  • P1: Exact email match — definite duplicate, merge immediately
  • P2: Name token overlap ≥80% AND same/shared company (fuzzy containment match)
  • P3: Name overlap ≥80% AND same job title (fuzzy) AND same city
  • P4: Same phone number — definite duplicate
  • Source priority: resume_upload > PDL > Naukri > Indeed > Shine > Foundit > TimesJobs > LinkedIn > CSE
  • URL priority: job board URL first > PDL > CSE/web_search
  • Writes and runs Python scripts (dedup.py) for deterministic matching on large sets
  • Name tokenization ignores middle initials (single-letter tokens like "K.", "A.")
Reads
03_raw_profiles.json — RawProfile[] from all fetching sources
Writes
04_deduped_profiles.json — DedupedProfile[] with dedup_rule (P1-P4/unique), alt_profiles
Candidate Ranking
.claude/agents/candidate-ranking.md
STAGE 5
Read Write WebFetch Bash

Scores every candidate against the SearchSpec using a weighted formula with a must-have gate. Verifies all URLs via WebFetch with alt_profile recovery, and writes personalized reasoning per candidate.

score = 0.50 × must_have_pct + 0.25 × nice_have_pct + 0.15 × seniority_proximity + 0.10 × location_match
  • Must-have gate: missing >1 must-have skill → auto-rejected regardless of score
  • Seniority proximity: 1.0 exact match, 0.5 one level off, 0.0 two+ levels off
  • Location match: 1.0 match, 0.8 remote, 0.5 unknown, 0.0 mismatch
  • URL verification via WebFetch — trusts existing url_status from Stage 3/4, only re-checks unknowns
  • Dead URLs trigger alt_profiles recovery (tries each alt URL in sequence)
  • Profiles with no reachable URL excluded from accepted/close buckets
  • Personalized 3–5 sentence reasoning per candidate (real data only, no templates)
  • Buckets: accepted (≥70% + all must-haves), close (≥50%), rejected
  • Writes and runs Python scoring scripts (score.py) for consistent arithmetic
Reads
04_deduped_profiles.json + 01_search_spec.json + 00_input.json (thresholds)
Writes
05_pipeline_output.json — accepted[], close[], rejected_count, execution_trace

run-pipeline Command

.claude/commands/run-pipeline.md — Orchestrates all 6 sub-agents with 3 human-in-the-loop checkpoints

The /run-pipeline slash command is the top-level orchestrator. It collects the job description interactively, initializes a run directory at /tmp/recruiting-pipeline/<run_id>/, determines fetch mode (API vs Web) from .env keys, and invokes each sub-agent in sequence. Between stages, it pauses at three HITL checkpoints where the recruiter can review, edit, or redirect the pipeline. Each stage is timed and the final output is rendered as a formatted shortlist with candidate profiles, scores, and reasoning.

HITL-1 — JD Review

After JD extraction, before search begins. Recruiter reviews the extracted SearchSpec — role title, must-have skills, inferred skills, quality score. Context-aware prompting highlights issues like low quality scores or missing fields.

Trigger: always fires after Stage 1
confirm edit fields abort

HITL-2 — Pool Size Check

After deduplication, if candidate pool is below 2x requested count. Analyzes source availability and dedup loss to recommend the best expansion strategy. Options are tailored to actual data — e.g. "relax location" is hidden if spec is already "Remote".

Trigger: deduped_count < requested_count × 2
broaden queries relax location proceed abort

HITL-3 — Shortlist Size Check

After ranking, if the shortlist is below requested count. Analyzes score distribution and rejection reasons (must-have gate vs low score vs dead URLs) to suggest targeted fixes. Options that would not help are automatically hidden.

Trigger: accepted + close < requested_count
lower threshold −10% include close proceed abort
